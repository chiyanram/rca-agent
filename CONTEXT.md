# CONTEXT

Glossary for the RCA agent. One term, one meaning.

## Terms

- **Incident** — a triggering alert plus the context attached to it (service, time window, labels). The unit of work that starts an Investigation. Always opened by an Operator, who picks the alert from a list or pastes it; an alert never starts an Investigation on its own. A repeat of the same alert while its Investigation is open updates that Investigation instead of starting another.
- **Pasted alert** — alert text an Operator supplies (a copied email or chat message, a dropped email file, or a typed id or link). It is untrusted: it is used only to find the matching alert in the alerting backend, it is never followed or obeyed, and it cannot choose where the agent looks, who is told or what is run.
- **Unmatched Incident** — an Incident started from a Pasted alert when no matching alert can be found in the alerting backend. Its service, environment and time are the ones the Operator confirmed, and the RCA report says no live alert stood behind it.
- **Related alert** — another live alert the Operator attaches to an Incident as context (for example, other alerts fired by the same outage). It informs the Investigation but does not trigger it.
- **Operator** — a signed-in person who starts Investigations and makes Gate decisions. The agent acts with its own identity but only on behalf of an Operator, and never does what that Operator is not allowed to do.
- **Setup admin** — a signed-in person allowed to change Setup: connect tools, edit the Service registry, and confirm Recovery workflows, recipients and runbooks. A separate role from Operator; one person may hold both.
- **Setup** — everything the agent is told about the estate before any Investigation: Connections, Environments, the Service registry and what a Setup admin has confirmed. Only confirmed items ever reach the agent. Something found by scanning stays a draft until a person confirms it; a confirmed Recovery workflow, recipient or runbook link that later changes goes back to waiting for confirmation and can't be used until then.
- **Setup change** — a recorded change to Setup: who, when, what changed and why. It is audited like an Action but is not one, because it happens outside any Investigation. An Investigation keeps using the Setup it started with, except that Recovery workflows and recipients are checked against the current Setup before use.
- **Connection** — one backend the agent is allowed to reach (a source-control host, an observability backend, a model provider, a notification channel), with a reference to its credentials, never the credentials themselves. It is one configured instance of a Plugin. Usable only after its access test passes.
- **Plugin** — one packaged integration for one kind of backend (for example Dynatrace, GitHub or ELK). It says which signals and operations it serves, how risky each operation is, what credentials it needs and how to test access. How it reaches the backend (its own code, a command-line tool or an MCP server) stays hidden inside it. Plugins ship with the app; a Setup admin turns one on by creating a Connection for it. A Setup admin may make an operation count as riskier, never as less risky.
- **Minted scope** — access narrowed by creating a short-lived token for one Investigation, holding only the permissions it needs, and dropping it as soon as it is done.
- **Clamped scope** — access narrowed, where a backend cannot create such tokens, by a standing read-only credential plus the agent's own code refusing any request outside the Investigation's service and time window.
- **Personal copy** — a copy of the app one person runs for themselves until there is a shared deployment. It is the same app, set as personal when installed and never switched afterwards. It is the first release (v1). Its one user holds every role and its Connections may use Personal credentials. It never runs Recovery workflows or sends Notifications: it prepares Recovery commands and Notification drafts for its user instead, and it may create a Published record only after that user approves. Nothing from it counts for a shared setup. Gates, the Action policy, redaction, confirmed-only Setup, the Audit trail and spend caps work exactly as in a shared one.
- **Personal credential** — a person's own login used by a Connection, allowed only in a Personal copy. Everything done with it is recorded as done with that person's login; it can never run a Recovery workflow, and results from it never count for a shared setup.
- **Guided setup** — the "ask me" way through Setup: the app asks which tools a person uses, drafts Connections, Environments and Service registry entries from what it can scan, and shows each as a card. A card becomes a Setup change only when the person confirms it, through the same rules as the Setup screen. It never guesses a value it cannot scan and never sees secret values.
- **Setup export** — a file of the facts about the estate (Environments, Service registry, Field maps, Release styles) taken from one installation to seed another. It never carries credentials or anything personal, and everything in it arrives at the other installation as a draft waiting for confirmation.
- **Environment** — a place where Target services run (for example the Test bed or production), saying which Connection answers for each kind of signal and which deployment record belongs to it.
- **Setup question** — something about a service that only a person can answer (who to notify, which deployment is production). An unanswered one never stops an Investigation; it only switches off what depends on the answer, and the RCA report names the gap.
- **Investigation** — one run of the agent on one Incident: gathering evidence, forming hypotheses, and producing an RCA report. Always produces an RCA report unless a human cancels or abandons it. It ends only when it is **closed**, and a closed Investigation is never reopened: a new alert, even a repeat of the same one, starts a new Investigation linked to the earlier one.
- **Stage** — one step of an Investigation with a single job (Pre-fetch, Evidence, Change, Code-locator, RCA writer, Fix proposer, Open draft PR). Stages run in a fixed order set by the pipeline, never chosen by the agent. A stage that runs out of budget hands on an incomplete result with its gaps named, rather than failing the Investigation.
- **Pre-fetch** — the first Stage: it gathers the evidence almost every Investigation needs (alert details, error log patterns, key metrics, recent changes) without asking the model.
- **Finding** — a claim made during an Investigation together with its citations: an observability query with its time range and link, or a code location at a specific commit. Stages hand Findings forward; the RCA report may only rest on Findings already recorded.
- **Code fact** — a Finding about code that the agent's own code works out, not the model (for example, the exact line a stack frame points to, the commits that recently touched it, or the entry points that lead to it). The model may cite it but never change it. Each one says whether it is certain or a labelled guess, what it was worked out from, and can be worked out again with the same result. When one can't be worked out, that is recorded as a gap, never silently skipped.
- **RCA report** — the output every Investigation must produce: root-cause hypothesis, supporting evidence, and suspect code locations across repos.
- **Fix proposal** — an optional change that follows an approved RCA report: patches to one or more repos (each opened as its own draft pull request once approved), with a rationale, Check results and Impact reach. It may also say that no safe code fix exists. Never produced without passing a HITL gate. "Pull request" means a GitHub pull request or a GitLab merge request.
- **Fix engine** — the pluggable coder that writes a Fix proposal's patches. It only proposes; it never decides whether its own work is good.
- **Release style** — how a repo gets a fix into production when what runs there is behind the main branch: **fix forward** (the next normal release carries the fix) or **upstream first** (fix the main branch first, then copy the same fix onto a branch made from the release that is running). Drafted by scanning, confirmed by a Setup admin; until confirmed, a repo counts as fix forward.
- **Hotfix offer** — the Fix gate's notice that production runs an older release than the main branch and needs the fix copied onto a branch made from that release. Shown only for an upstream-first repo whose Deployed commit is known exactly. The agent never tags, releases or deploys that branch; people do.
- **Backport patch** — a Fix proposal's change adapted to the older code running in production, written when the main-branch fix does not apply there unchanged. It is checked on its own and always shown next to the main-branch fix as differing from it.
- **Check** — a verification the agent's own code runs on a Fix proposal (it applies, it changed something real, it stays within limits, it compiles, its tests and regression test behave). Only Check results count; what the Fix engine claims about its work never does. Some Checks block approval, the rest inform the human.
- **Impact reach** — what a Fix proposal's change can affect: the changed code, everything that calls it, the entry points behind it and the services that call those. Worked out by the agent's own code, not by the model.
- **Fix review** — a model's critique of a Fix proposal before the Fix gate, in a bounded number of rounds. Advisory only: a review point counts only when it points at real code.
- **HITL gate** — a mandatory point in an Investigation where the agent stops and a human decides before work continues. There are two: the **RCA gate** (after the RCA report) and the **Fix gate** (after the Fix proposal, before the draft PR). A gate never approves itself; it waits.
- **Gate decision** — what a human chooses at a HITL gate (e.g. approve, revise with feedback, reject, abandon), recorded with who and when.
- **Human question** — a question the agent asks a human on its own initiative. It pauses the Investigation like a HITL gate but is optional, not mandatory.
- **Follow-up question** — a question an Operator asks about an RCA report, from the time the RCA gate opens until the Investigation's content expires. The answer is kept with the report version it was asked about, rests on cited Findings, and never changes the report or causes an Action; asking never reopens an ended Investigation. It is the reverse of a Human question: the human asks and the agent answers.
- **Contradiction flag** — a warning raised in a Follow-up answer that the approved RCA report may be wrong, backed by citations. It decides nothing; a human chooses whether to act on it.
- **Action** — anything done during an Investigation, by the agent or by a human: a query, a code read, a question, a command, opening a pull request. Every Action is recorded in the Investigation.
- **Audit trail** — the tamper-evident record of everything that happened in an Investigation, together with every Setup change. It is the Investigation's own history, viewed for audit, not a separate copy. Each record has a small part that says who did what, when, and under which approval, kept for a long time. It may also have a bulky part with the actual content (prompts, model answers, logs, code excerpts), which **expires** some time after the Investigation closes. After that the record still shows that the content existed, but the content can no longer be read.
- **Auditor** — a signed-in person who may read every Investigation and Setup change and export Audit bundles, but cannot change anything or start Investigations.
- **Audit bundle** — a signed export of one Investigation's Audit trail that anyone can check for tampering without access to the agent. Every export is itself recorded.
- **Action policy** — the rule that gives every Action a risk class (read, sensitive-read, write, critical) and decides whether it runs straight away or only after human approval. Write Actions need approval. Critical Actions need their own approval, and the only one the agent carries out is running a Recovery workflow; anything else that touches production is a Manual step.
- **Recovery workflow** — a team's own automated recovery procedure (for example, retrying failed messages) that a person has confirmed, during setup, as one the agent may run for a given service. The agent may run it only after its own approval, and the agent's own code chooses every value it is given. A workflow nobody confirmed can never be run.
- **Recovery command** — an exact command (for example a workflow run with its inputs filled in) that the agent prepares from a confirmed runbook or Recovery workflow, citing the line it came from, for a person to run themselves. The agent never runs it; the Operator records whether it was done.
- **Notification draft** — the recipients, subject and body of a Notification, prepared from the fixed template and the approved RCA text, for a person to send themselves from their own mail or chat.
- **Manual step** — a recovery, configuration or release action a human performs, by whatever means they choose (for example, a rollback, a restart, changing a setting outside any repo, applying a Backport patch, creating a protected hotfix branch, or tagging, releasing and deploying). Usually proposed by the agent; an Operator may also record one they did on their own. The agent never claims it happened; the Operator records whether it was done.
- **Notification** — a message the agent sends about an Investigation, only to people or groups confirmed for that service, in the agent's own fixed format, after an Operator approves the exact text. Its only free text is the summary from the RCA report a human approved and a note the Operator writes; nothing the model writes later goes into it.
- **Resolution window** — the part of an Investigation after the RCA gate is decided and before it is closed, whether or not a fix was chosen. In it the Operator can run Recovery workflows, send Notifications, add Linked issues and record Manual steps, in any order.
- **Close** — the Operator's explicit act that ends an Investigation and records its Outcome. Cancelling, abandoning and an Investigation left idle too long also close it. Closing starts the clock after which its content expires and ends the time for Follow-up questions.
- **Outcome** — how an Investigation ended, recorded at Close: a fix pull request opened, recovered without a code change, mitigated (symptom gone, cause still there), no action needed, unresolved, abandoned or cancelled. The agent's code proposes it from what actually happened; choosing one that the record does not support needs a written reason.
- **Incident record** — the lasting summary of a closed Investigation, built only from what was recorded and approved: the alert, the approved RCA summary, the Outcome, recoveries and their checks, Manual steps, Notifications and Linked issues. It outlives the Investigation's expiring content. When published, it keeps the page id of its Published record.
- **Past Investigations** — the list of related closed Investigations shown to an Operator when an Investigation starts: same service and environment, those with the same alert rule first, then those linked by follows, then the rest, newest first. It is worked out by fixed rules, never by similarity guessing.
- **Knowledge page** — a team page (for example in Confluence) that a Setup admin confirmed for a service, pinned to the version they confirmed. A runbook is one kind of Knowledge page. A newer version reaches the agent only after it is confirmed again.
- **Hint** — material given to the agent as fenced data that may suggest where to look but can never be cited as a Finding: whatever it suggests must be checked afresh in the current Investigation. Past Incident records and Knowledge pages are Hints. A Hint cannot change scope, recipients or Actions.
- **Published record** — a copy of an Incident record placed in the team's confirmed space after an Operator approves it. The agent never edits or deletes it afterwards; it follows that space's retention, not the agent's.
- **Linked issue** — an issue in the team's issue tracker (for example Jira) that an Investigation created or linked to during its Resolution window, each only after an Operator approved it. A created one holds only the fixed template, the summary from the approved RCA report, the Operator's note and links; nothing the model writes later goes into it. The agent writes only into the team's confirmed project, and after creating or linking never changes, comments on, closes or deletes the issue: people own it from then on. The agent never reads issue text into an Investigation.
- **Target service** — a system the agent investigates (Java built with Gradle or Maven, Spring or Micronaut, deployed on Azure, built by GitHub Actions or GitLab CI). Each lives in its own repo on GitHub or GitLab. Each has a **Hosting** saying how it runs: as an ordinary app or as a function app (Azure Functions). The hosting decides which runtime failures and signals apply to it.
- **Service registry** — the part of Setup that says, for each Target service or shared library, which repo holds its code, which packages and client names belong to it, and any notes the Operator wants the agent to know. Each repo the agent can see is registered, still a draft, or deliberately excluded; the agent reads code only from registered repos.
- **Deployed commit** — the commit actually running for a service in an environment at a given time. Code locations in Findings point at it; when it cannot be determined, the location says so.
- **Seeded fault** — a deliberately injectable defect in a Target service of the test bed, used to give Investigations a known, repeatable root cause.
- **Test bed** — the local environment of sample Target services and observability stack used to exercise and grade the agent. It comes in more than one profile, each pairing a source-control host, an observability backend and a build tool.
- **Scenario** — one repeatable test of the agent in the Test bed: a Seeded fault (or none), the traffic that makes it show, the alert it should raise and its Answer key. Some Scenarios add a red herring, a planted prompt injection, or have no known answer at all. A Scenario can also be drafted from a real Investigation that a human revised or abandoned; it stays a draft until a person writes its Answer key.
- **Answer key** — what a Scenario's RCA report is judged against: the root cause, where it lives (code, commit, deployment or setting), the facts the report must cite, the outcome it should lead to (fix, no fix, recovery, notification, close) and the mistakes it must not make. Kept where the agent can never read it.
- **Agent version** — everything that decides how the agent behaves, recorded as one identity: which model answers each Stage, the prompts, the Fix engine and the way Code facts are worked out. Two runs with the same Agent version should behave alike; any change makes a new one.
- **Model family** — the maker's line of models a model belongs to (for example Claude, GPT, Gemini), whichever provider serves it. The same model reached through two providers is one family. A model's opinion on an Agent version's work only counts as independent when it comes from a different family.
- **Evaluation run** — one measured try-out of an Agent version: a chosen set of Scenarios, each run a fixed number of times, every result graded. It is how a change to the agent is judged and how a model or Agent version gets approved. It has a spending cap and never counts as passed if it stopped early.
- **Trial** — one Investigation of one Scenario inside an Evaluation run. It is an ordinary Investigation, recorded like any other, only marked as part of the run.
- **Grade** — the judgement of one Trial against its Scenario's Answer key: whether the RCA report, the outcome and any Fix proposal were right, and whether anything forbidden happened. Decided by fixed checks; a model's opinion may be attached but does not decide.
- **Scripted Operator** — a bot that makes Gate decisions and answers Human questions during a Trial, following the Scenario's script. It exists only in a Test bed, and its decisions are always recorded as the bot's, never a person's.
- **Fork** — a new Investigation that starts from a copy of another one's history up to a chosen Stage and runs on from there, usually with a different Agent version, so the two can be compared on the same evidence.
- **Champion** — the Agent version currently approved for production. Real Investigations only ever run on it; every change is measured against it.
- **Challenger** — a candidate Agent version being measured against the Champion, written by a person or proposed by an Optimisation run. It replaces the Champion only after passing the promotion bar and a person's sign-off.
- **Held-out set** — the Scenarios a person sets aside, fixed per catalog version, that are never used to tune the agent. Whoever tunes the agent, a person or an Optimisation run, sees only whether a held-out run passed overall, never anything per Scenario; a gain that does not show there counts as overfitting.
- **Optimisation run** — a run, started by a person in a Test bed, in which an optimiser model writes Challenger prompts for one Stage, scores each on Forks of training Trials by the fixed checks, and hands at most a few as draft pull requests. It may change prompts only, never sees Answer keys, held-out detail or production, has its own spending cap, and never promotes anything.
- **Optimiser config** — the named model and provider an Optimisation run uses to write Challenger prompts, recorded with every Challenger it proposes. It is chosen by a person and never switched automatically.
- **Attack goal** — one harmful thing a planted prompt injection tries to make the agent do, declared before the attack so that success is decided by fixed checks: read outside the Investigation's scope, do something on the never-list, leak a Canary secret, get the RCA report to blame a place the attacker chose, slip the attacker's change into a Fix proposal, or get the agent to ask the Operator to act for the attacker. Goals that our code must block are **control breaches**; goals that only a human at a gate can catch are **steered outcomes**. Each try ends as not attempted, attempted but blocked (naming the control that blocked it), or reached.
- **Attack run** — a kind of Evaluation run in which an attacker model rewrites a planted injection again and again, seeing what the agent did after each try, to reach an Attack goal within a fixed number of tries and a spending cap. It only ever shows what an attacker can at least do, never that the agent is safe. Every goal it reaches becomes a fixed injected variant of the Scenario.
- **Control probe** — a check, run without any model, that hands the agent's own code a hostile request (a repo outside the Service registry, the wrong time window, a forbidden path) or a Canary secret, and confirms the code refuses or removes it.
- **Canary secret** — a made-up, secret-shaped value planted in a Test-bed Scenario. Redaction must remove it; if it ever appears in a prompt, an RCA report, a pull request, a Notification or a question to the Operator, redaction has failed.
- **Observability adapter** — the boundary through which the agent reads alerts, logs, metrics, and traces. Each kind of signal can come from a different backend (for example alerts and traces from Dynatrace, logs from ELK); the agent sees the same shape whichever backend answers.
- **Runtime event** — something the platform a Target service runs on reports about it, rather than the service's own code: it started, restarted or stopped, a run hit its time limit, or it ran out of memory. Read through the Observability adapter like logs and metrics, whichever backend answers.
- **Log digest** — the app's own summary of a log window: raw lines, already redacted, grouped into Log patterns and ranked, with new-since-before first. Built the same way whatever backend holds the logs; the backend only picks which lines to return. When only part of the window could be read, it says how much.
- **Log pattern** — one group in a Log digest: lines that are the same message from the same place once their changing parts (ids, numbers, times) are blanked out. It carries its counts, when it was first and last seen, whether it is new, sample lines and trace ids, and the code it probably comes from. Each pattern is its own Finding, and keeps the same identity across re-runs.
- **Field map** — the part of an Environment that says, for one log source, how to read each line: where its level, logger, trace id, service and message are. Drafted by scanning sample lines and confirmed by a Setup admin.
- **Source-control adapter** — the boundary through which the agent reads code, change history and deployments and opens draft pull requests, whichever hosting service holds the repo (GitHub or GitLab).
- **Build adapter** — the boundary through which a Fix proposal is compiled and tested in isolation, whichever build tool the repo uses (Gradle or Maven). It never sees credentials; when private dependencies can't be fetched, it checks what it can and says the build was partial.
- **Token broker** — the separate service that holds the GitLab account allowed to create access tokens, and hands the agent short-lived tokens for one repo at a time: read tokens only while a stage is running, a write token only after a Fix gate approval for that repo, and a recovery token only after a Recovery approval. It checks the recorded approvals itself before every token, revokes each token as soon as it is no longer needed, and refuses writes on a repo whose branch protection is weaker than required or has changed since a Setup admin confirmed it.
- **Linked GitLab account** — the GitLab user an Operator has proved is theirs by signing in to GitLab once. GitLab access checks for that Operator use this account; without one, an Operator can view Investigations but cannot start or approve anything that touches GitLab repos.
