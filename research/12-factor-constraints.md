# 12-factor agents → design constraints for the RCA agent

Resolves issue #3. Vocabulary per `CONTEXT.md` (Incident, Investigation, RCA report, Fix proposal, HITL gate, Target service, Observability adapter).

**Primary source:** [humanlayer/12-factor-agents](https://github.com/humanlayer/12-factor-agents), read at commit [`d20c728`](https://github.com/humanlayer/12-factor-agents/tree/d20c728368bf9c189d6d7aab704744decb6ec0cc) (all 12 factor pages, the "Factor 13" pre-fetch appendix, and the README). Citations below use `[Fn]` for `content/factor-NN-*.md`, `[F13]` for `content/appendix-13-pre-fetch.md`, `[README]` for the README. Links are at the bottom.

Labels used in the table:

- **Sourced**: the constraint restates what the factor page says.
- **Inferred**: my application of the factor to this agent. The source does not mention RCA, AG-UI, Claude or Grafana.

## Answer in one paragraph

The 12 factors amount to one architecture. An **Investigation is an append-only, serializable event thread** (F3, F5, F12). A **pure "determine next step" function** turns that thread into a typed intent (F1, F4). An **owned loop** runs read-only intents inline. It **persists and exits** on intents that need a human or a long wait, and resumes from a webhook or AG-UI action (F6, F7, F8). The work is split into **several small agents with 3–20 steps each**, joined by a mostly deterministic Investigation pipeline (F10). The pipeline **pre-fetches the obvious evidence** before the first LLM call (F13). For this agent, the hardest constraint is a pause **between tool selection and tool invocation** that survives a restart, applied to `open_fix_pr` and other gated actions (F8). That requirement, plus owning prompts and context (F2, F3), is where frameworks push back. A framework is acceptable only if it passes the four checks listed under "Framework tensions".

## Factor → constraint → design implication

| # | Factor | Constraint on the RCA agent | Design implication | Framework tension |
|---|---|---|---|---|
| 1 | Natural language to tool calls | The LLM's only job per step is to turn context (alert, evidence, human text) into **one structured next-step object**. Deterministic code acts on that object. *(Sourced: [F1])* | Define a closed set of typed intents, e.g. `query_logs{logql,range}`, `query_metrics{promql,range}`, `get_trace{id}`, `list_deploys{service,since}`, `search_code{repo,query}`, `read_file{repo,path,lines}`, `request_human_input{…}`, `submit_rca_report{…}`, `propose_fix{…}`, `done`. The switch on intent lives in our code. Unknown intents go to an explicit fallback branch. *(Inferred)* | Low. Every framework does tool calling. |
| 2 | Own your prompts | Prompts are **first-class code**: version-controlled, testable, evaluable, with no framework-generated "role/goal/personality" wrappers. *(Sourced: [F2])* | Keep prompts as templates in the repo, one per small agent. Tie prompt changes to the eval harness, where Seeded-fault Investigations act as regression tests. Behind the thin Claude model interface, the only input is a rendered prompt plus a tool/output schema. *(Inferred)* | **High** for agent-abstraction frameworks (`Agent(role=…, goal=…)`). [F2] names this pattern as hard to tune. A framework must let us supply the exact system and user text. |
| 3 | Own your context window | We decide what goes into each call and in what format. A custom, dense format (e.g. XML-ish event blocks) is allowed in place of the standard message list. Resolved errors can be dropped. **Sensitive data is filtered** before it reaches the LLM. *(Sourced: [F3])* | (a) A `thread_to_prompt` renderer turns Investigation events into compact tagged blocks. (b) Observability adapters return **summaries**, never raw dumps: Loki log-pattern clusters and counts with a few exemplars, Prometheus series as reduced stats, Tempo traces as the critical-path spans. (c) Strip secrets and PII before rendering (feeds #14). (d) Log and code content always sits inside delimited data blocks, which gives a fixed boundary for prompt-injection handling (#14). *(Inferred)* | **Medium–high.** Frameworks that own the message history, or that hide tool results from the developer, conflict with this. We need a hook to render the whole context ourselves on every turn. |
| 4 | Tools are just structured outputs | A "tool call" is JSON that **describes** what deterministic code should do. The code may execute it differently, or not at all. *(Sourced: [F4])* | The executor validates and **rewrites** intents before running them: clamp time ranges, cap Loki line limits, force the Target service's label selectors, restrict `read_file` to allow-listed repos. Split intents into **read-only** and **mutating** (`create_branch`, `open_fix_pr`). Mutating intents run only from an approved state. *(Inferred)* | Medium. Frameworks that bind a tool name directly to a function and auto-invoke it remove the gap between "model chose X" and "X ran". Calling Claude's tool-use API directly is compatible, because tool_use blocks are already just structured output. |
| 5 | Unify execution state and business state | Derive execution state (current step, waiting, retry counts) from the event thread wherever possible. Keep out-of-band state (session ids, credentials) to a minimum. *(Sourced: [F5])* | The Investigation **is** its event log. Status (`gathering`, `awaiting_rca_approval`, `awaiting_fix_approval`, `done`) is a projection of the log, not a separate state machine. The log is the single source for resume, fork (re-run from event N with a new prompt), audit, and the AG-UI view, which [F5] lists as "trivial to convert a thread into … a rich Web app UI". Credentials stay outside the thread. *(Inferred)* | Medium. Frameworks with their own checkpoint or graph state create a second source of truth next to our domain events. |
| 6 | Launch/pause/resume with simple APIs | Users, apps, pipelines and other agents can **launch** with a simple API. Orchestrating code can **pause**. External triggers such as webhooks **resume** without deep integration into the orchestrator. *(Sourced: [F6])* | Expose `POST /investigations` (launch from an Alertmanager webhook, AG-UI or CLI), `GET /investigations/{id}` (status and thread), and `POST /investigations/{id}/events` (resume with a human response or an async result). AG-UI is one client of these endpoints, not the owner of the run. *(Inferred)* | **High.** [F6] notes that orchestrators "often … allow for pause and resume, but not between the moment of tool selection and tool execution". |
| 7 | Contact humans with tool calls | Asking a human is an **intent like any other** (`request_human_input` with question, context, urgency, format, choices). The loop saves state, notifies, and **exits**. The human's response comes back as an event. The flow can start `Agent→Human`, as when an alert or cron triggers the run. *(Sourced: [F7])* | (a) Two kinds of HITL: **model-initiated** (clarify scope, ask for a missing repo) and **deterministic, mandatory gates** (RCA approval before any Fix proposal; fix approval before `open_fix_pr`). The mandatory gates are enforced by the pipeline, not left to the model. (b) Human responses are recorded with user, timestamp and decision, which gives an audit trail. (c) The same intent later maps onto Slack/Teams (map "Not yet specified"). The AG-UI screen should render `options.format` (yes_no / multiple_choice / free_text). *(Inferred)* | Medium. Frameworks with in-process `input()`-style human tools break the save-and-exit model. |
| 8 | Own your control flow | Build our own loop. It knows which intents are **sync** (run, append, continue) and which are **async** (break, persist, wait). Interrupting **between tool selection and invocation** is the central capability. Custom hooks are allowed: summarization or caching, LLM-as-judge, compaction, tracing, rate limiting, durable sleep. *(Sourced: [F8])* | (a) Read-only evidence intents are sync. `request_human_input`, `submit_rca_report` (which triggers the RCA gate) and `open_fix_pr` are async. (b) `open_fix_pr` is **persisted as a selected-but-not-executed event** and runs only after the matching approval event arrives. (c) Per-agent step, token and wall-clock budgets. (d) An optional LLM-as-judge check on the RCA report before it reaches a human. (e) OpenTelemetry spans around each step. Without (b), [F8] says you are forced into in-memory waits, low-stakes-only tools, or "yolo". *(Inferred)* | **Highest.** [F8] calls this "the number one feature request … for every AI framework". This is the deciding test for #4 and #8. |
| 9 | Compact errors into context window | Feed tool errors back as compact events so the model can self-heal. Cap consecutive errors (about 3). After that, escalate to a human or take over deterministically. Errors may be restructured or removed instead of appended raw. *(Sourced: [F9])* | A bad LogQL/PromQL query or a missing file path becomes a one-line `<error>` event, with the query echoed and the backend's parse message. Use a per-tool consecutive-error counter. At the threshold, emit a `request_human_input` or abort that sub-agent with a partial result. Hide resolved errors when rendering (F3). *(Inferred)* | Low. [F9] says "most frameworks implement this". Check that the retry policy and error rendering can be changed. |
| 10 | Small, focused agents | Each agent covers one domain with **3–10, maybe 20 steps max**. Agents are building blocks inside a mostly deterministic system. Grow the scope only while quality holds. [F9] calls this the number one defence against error spin-outs. *(Sourced: [F10], [F9])* | Do not build one big RCA agent. Use a deterministic **Investigation pipeline** of small agents. Example split: **Evidence agent** (observability adapters), **Change agent** (deploys, commits, PRs, Actions runs in the window), **Code-locator agent** (multi-repo search and read, #5/#11), **RCA writer** (composes the report from collected evidence), and **Fix proposer** (after approval). Each agent gets its own prompt, intent set, and step budget. Agents hand off through typed results appended to the parent thread. *(Inferred)* | Medium. Multi-agent "crew" frameworks push autonomous delegation between agents. [F10] wants deterministic orchestration between agents and agentic behaviour only inside each one. |
| 11 | Trigger from anywhere | Launch from any channel (Slack, email, SMS, events, crons, *outages*). Respond on the same channel. "Outer-loop" agents run 5–90 minutes and contact a human at critical points. Fast human loop-in makes higher-stakes tools acceptable. *(Sourced: [F11])* | The primary trigger is an **Alertmanager webhook**. That is an outage-triggered, outer-loop run with no human present at the start. AG-UI is the primary HITL surface but must not be the only entry point. Later: Azure Monitor alerts and Slack/Teams. Each channel is a thin adapter onto the F6 API. *(Inferred)* | Low–medium. Chat-centred frameworks assume `Human→Agent` turn-taking. |
| 12 | Make your agent a stateless reducer | The agent is a fold over events: `(state, event) → state`. *(Sourced, but the page is only two diagrams: [F12])* | `next_step = f(thread)` is a pure function except for the LLM call, and side effects live in the executor. This makes **replay** possible. A recorded Investigation can be re-run against a new prompt or model and diffed, which is the basis for the evaluation harness (map "Not yet specified"). The agent process holds no state, so it can scale horizontally and recover from crashes. *(Inferred)* | Medium. Frameworks with hidden in-memory agent objects or memory modules break the reducer model. |
| 13 | (appendix) Pre-fetch all the context you might need | If a tool call is highly likely, **call it deterministically** and put the result in context instead of spending a model round-trip. *(Sourced: [F13])* | At Investigation start, before any LLM call, the pipeline fetches the alert payload and labels, a Loki error-pattern summary for the service and window, RED/USE metrics around the alert time, the last N deploys/commits/Actions runs for the service's repo, and the service → repo mapping. These become the opening thread events. This saves several turns per Investigation and shortens the agent's own step count (F10). *(Inferred)* | Low. Fits any runtime, but needs a pre-processing hook ahead of the agent loop. |

## Framework tensions (for #4 and #8)

The README puts the framework argument plainly. Teams "grab $FRAMEWORK", reach 70–80% quality, "realize that getting past 80% requires reverse-engineering the framework, prompts, flow, etc.", and "start over from scratch". The recommended path is to "take small, modular concepts from agent building, and incorporate them" into your own software. The README also says this is "BY NO MEANS meant to be a dig" on frameworks, and that you "will get most/all" of the core principles from one. *(Sourced: [README])*

The factors that push hardest against frameworks are, in order: **F8 (interrupt between selection and invocation) > F2 (prompts) > F3 (context) > F6 (pause/resume API) > F5/F12 (state ownership)**. F1, F9, F11 and F13 fit almost any runtime.

**Four pass/fail checks** for any runtime candidate in #4. This is my distillation, not text from the source:

1. **Exact prompt text.** Can we supply the full system and user content ourselves, with no injected scaffolding? (F2)
2. **Custom context rendering.** Can we build the model input from our own event log on every turn, rather than from the framework's message history? (F3, F5)
3. **Durable pause between tool selection and invocation.** Can a selected `open_fix_pr` be persisted, the process stopped, and execution resumed hours later after an approval event? (F6, F8)
4. **Exposed step function.** Can we call one "next step" at a time from our own loop, for replay and evals? (F8, F12)

A runtime that fails check 3 is disqualified for the fix path. It could still serve the read-only evidence agents. If no candidate passes all four, the default implied by 12-factor is a **hand-rolled loop** (a few hundred lines) on the Anthropic SDK plus an AG-UI server SDK, with the event store in a database.

## Implications for other tickets

- **#2 (AG-UI)**: Confirm that AG-UI lets a run **end** on an interrupt and that a later run resumes by thread id, rather than holding a live connection open while it waits for approval (F6/F7/F8). AG-UI events should be a projection of our Investigation thread, not its source of truth (F5).
- **#4 / #8 (runtime)**: Use the four checks above as acceptance criteria. Check 3 is the deciding one.
- **#9 (HITL gates)**: Separate model-initiated `request_human_input` from **deterministic mandatory gates**: RCA approval, then fix approval before `open_fix_pr`. Gate decisions are events carrying user, time and decision. Timeout means the run stays paused, never auto-approved. F7 and F11 describe these runs as outer-loop runs with no human present at start.
- **#10 (state)**: Effectively decided by F5/F6/F12. An append-only Investigation event log is the single source of truth. Status is derived from it. Resume works by loading the log. Fork and replay come for free.
- **#5 / #11 (code across repos)**: The Code-locator is a small agent (≤20 steps) with read-only intents. The service → repo map and recent changed files are pre-fetched (F13).
- **#6 (Grafana APIs)**: Adapters must return **summarized** evidence (log pattern clusters, reduced metric stats), not raw payloads (F3). Echo query errors compactly (F9).
- **#14 (security)**: F3 makes filtering before the LLM, and fencing log/code content as data, part of context rendering, so they belong in the design rather than as add-ons.
- **Evaluation harness** (map "Not yet specified"): F2 and F12 make prompt and model regressions testable by replaying recorded threads against Seeded faults. This supports promoting the harness into the MVP spec.
