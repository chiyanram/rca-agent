# The agent never changes production directly

Restart, rollback, scale, configuration outside a repo, secrets and alert silencing are **Manual steps**: the agent proposes them with options and the exact how-to, a human performs them, and the Operator records whether they were done. The only critical Action the agent itself carries out is dispatching a **Recovery workflow** that a Setup admin confirmed for that service, after its own approval, with inputs our code fills in (at most 3 per Investigation). Code and in-repo config changes go only through the Fix gate as draft pull requests, never merged by the agent. We chose this over letting the agent run remediation because an RCA can be wrong, and a wrong automated rollback or restart in production costs far more than a few minutes of human action; automation grows by confirming more Recovery workflows, not by widening the agent's permissions.

Decided in [Which critical Actions may the agent take, and under what approval?](https://github.com/chiyanram/rca-agent/issues/17) and [How does an Investigation end without a code fix (recovery path, notify, close)?](https://github.com/chiyanram/rca-agent/issues/30); confirmed for Azure Functions in [Does the Test bed get a Kubernetes profile, and which pod-level Seeded faults does it add?](https://github.com/chiyanram/rca-agent/issues/32).

## v1 note

**v1 (laptop copy):** the agent dispatches nothing. It prepares **Recovery commands** (only `gh workflow run …` with inputs filled in). Our code checks each one every time: the workflow exists on the default branch, every input is declared, and it targets this service. Each command cites the runbook line and the workflow line. The person runs them. A step that fails the check becomes a Manual step. After one is marked done, a read-only post-check shows whether the alert stopped. Recovery workflows run by the agent are v2 ([`docs/releases.md`](../releases.md), [ADR-0006](0006-first-build-is-the-laptop-copy.md)).
